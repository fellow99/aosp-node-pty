# 000 · 工程规划 — `aosp-node-pty`

> 版本：v0.1（立项规划）
> 定位：本文件是 `aosp-node-pty` 的**唯一规划基线**。它回答三个问题——这是什么、它与
> [`aosp-node-runtime`](https://github.com/fellow99/aosp-node-runtime) 如何配对、它如何被
> 任意宿主工程以一致方式消费。所有实现、CI、发布、门禁设计均以此为准；变更走"先改本文件，再改实现"。
> 配套阅读：`aosp-node-runtime` 的 `README*.md`、`runtime.lock.json`、`tools/provision.mjs`、
> `.github/workflows/build-node-android.yml`。

## 1. 背景与定位

### 1.1 一句话定位

**以 AAR 形式发布的、与某个 Node.js 版本严格配对的 Android 版 [node-pty](https://www.npmjs.com/package/node-pty) 原生件**——
一份交叉编译的 `libpty_node.so`（arm64-v8a），在应用进程内被内嵌 Node 运行时（`libnode.so`）
经 N-API 加载，提供伪终端（`forkpty`/`openpty`）能力。

### 1.2 为什么需要它

- 生态**没有现成的 Android arm64 node-pty 预编译件**：node-pty 以"npm 源码 + 安装期本地编译"分发，
  而 Android 应用内的 Node 是内嵌共享库（无系统 node、无标准构建环境），无法在设备上 `node-gyp`。
- node-pty 的 UNIX 目标很小（`src/unix/pty.cc`，外加 `spawn-helper.cc`），但它是 **N-API 原生插件**，
  必须满足两条硬约束才能在内嵌 Node 中加载：
  1. **NODE_MODULE_VERSION 对齐**——`.so` 必须针对与运行时完全一致的 Node 头文件版本编译；
  2. **符号可达**——宿主往往以 `RTLD_LOCAL` 加载 `libnode.so`，普通 `dlopen` 解析不到 `napi_*` /
     `node_*` 符号；必须让产物带 `DT_NEEDED: libnode.so`，由动态链接器按 soname 复用已加载的引擎。
- 上述两点决定了：**pty 原生件不能脱离具体的 Node 运行时版本独立编译/发布**。它天然是运行时的"配对件"。

### 1.3 边界（本仓库做什么 / 不做什么）

| 在范围内 | 不在范围内 |
|---|---|
| node-pty **原生件**的交叉编译、ELF 门禁、AAR 打包、发布 | 任何嵌入 API / Kotlin/Java 桥（由 `aosp-node-bridge` 一类工程负责） |
| 版本配对事实源 `pty.lock.json`（版本 + sha256 + 配对 Node + 门禁） | Node 引擎本身（`libnode.so` 由 `aosp-node-runtime` 提供） |
| 可复现的 NDK 构建脚本与 GitHub Actions | 终端 UI、PTY 之上的会话/协议封装（由各宿主应用自行实现） |
| node-pty **JS 运行时封装**的版本对齐说明与消费契约 | 替消费方决定加载路径、ABI 名以外的产品策略 |

> 本工程**只产出与维护原生二进制及其可复现构建**，与具体宿主产品解耦。任何内嵌 Node 的 Android
> 工程都可以作为消费方，按 §7 的契约接入。

## 2. 与 `aosp-node-runtime` 的配对关系（核心约束）

`aosp-node-pty` 是 `aosp-node-runtime` 的**伴生制品（companion artifact）**，不是独立版本线。

### 2.1 版本号规则

1. **`aosp-node-pty` 的版本号恒等于其所配对的 Node.js 版本号**，与 `aosp-node-runtime` 完全一致。
   例：针对 Node `24.22.1` 编译的 pty 件，版本就是 `24.22.1`。
2. 该版本同时是：
   - node-pty 编译所用的 **Node 头文件版本**；
   - 运行时必须匹配的 **NODE_MODULE_VERSION**（如 Node 24.x = 137）；
   - `DT_NEEDED libnode.so` 所兼容的引擎版本；
   - Maven 坐标的 `version` 段。
3. **不引入独立 semver**。node-pty 自身的上游版本（如 `1.1.0` / `1.2.0-beta.x`）记录在 lock 的
   `builtFrom.nodePty` 字段作为**出处**，但不进入制品版本号——否则会制造"pty 版本 ↔ Node 版本"的多对多歧义。
   若需要在同一 Node 版本下重发（仅换 node-pty 上游补丁级版本），走 §8.3 的**构建序号**而非改主版本。

### 2.2 配对矩阵（一对一是硬约束）

| `aosp-node-runtime` | `aosp-node-pty` | 关系 |
|---|---|---|
| `io.github.fellow99:node-runtime:24.22.1` | `io.github.fellow99:node-pty:24.22.1` | 头文件版本、NODE_MODULE_VERSION、`libnode.so` soname 三者一致 |
| `…:node-runtime:22.23.4` | `…:node-pty:22.23.4` | 同上（若启用该矩阵） |

- pty 制品的 `gates` 必须断言 `DT_NEEDED` 含 `libnode.so` 且 `e_machine=aarch64`、`e_type=ET_DYN`、
  无 `PT_INTERP`（与 runtime 的 ELF 纪律一致）。
- **不保证跨 Node 大版本兼容**：为 24.x 编译的 pty 件在 22.x 引擎上属未定义行为（NODE_MODULE_VERSION 不符），
  消费方必须让两者版本严格相等。

### 2.3 对运行时的依赖形态

- **编译期**：需要该 Node 版本的**头文件**（`node-v<ver>-headers.tar.gz`，nodejs.org 官方 dist，
  与 runtime 同源、同 sha 纪律）以及一份 `libnode.so` 用于链接期符号解析（仅链接，不打包进 pty AAR）。
- **运行期**：消费方的 APK 中必须同时存在与 pty **同版本**的 `libnode.so`（由其引入
  `io.github.fellow99:node-runtime:<ver>` 提供）。pty 件自身**不携带也不重分发 `libnode.so`**，
  避免一份 APK 内出现两份引擎。
- Gradle 侧建议把 `node-pty` 标为与 `node-runtime` 同版本的配对依赖（见 §7.2），但本工程不发布
  聚合 POM 强制绑定——由消费方按矩阵选版本，保持"原生件仓库"的单一职责。

## 3. 技术方案

### 3.1 制品形态

```
node-pty-<ver>.aar
└── jni/arm64-v8a/libpty_node.so      # node-pty 原生件（ET_DYN，无 PT_INTERP，DT_NEEDED libnode.so）
```

- 环境：`minSdk 24` · ABI `arm64-v8a`（与 runtime 当前矩阵一致；后续按 runtime 同步扩矩阵）。
- 产物**只有这一个 `.so`**；不含 `libnode.so`、不含 `libc++_shared.so`（二者由 runtime 提供/统一供给）。
- 命名为 `libpty_node.so` 而非上游默认的 `pty.node` 的原因：
  - Android 打包/`System.loadLibrary` 与 nativeLibraryDir 只识别 `lib*.so` 形态；
  - targetSdk ≥ 29 的 SELinux `neverallow execute:app_data_file` 禁止从应用可写数据目录 `dlopen`，
    **唯一合规执行位是 APK 解出的只读 nativeLibraryDir**。
  - 上游 node-pty 的 JS 默认按 `build/Release/pty.node` 定位原生件；§7.3 给出消费方的装载适配契约。

### 3.2 源与工具链

| 项 | 取值 | 说明 |
|---|---|---|
| 源 | node-pty npm 包（**不改源码**） | UNIX 目标主体为 `src/unix/pty.cc`；`spawn-helper.cc` 仅特定平台需要，Android 走 `forkpty` 单文件 |
| N-API 封装 | `node-addon-api`（C++ 头，随 node-pty 依赖固定版本） | 与所用 node-pty 版本匹配 |
| Node 头文件 | `node-v<ver>-headers.tar.gz`（nodejs.org dist，可走镜像） | **版本必须等于配对 runtime** |
| 链接引擎 | 配对版本的 `libnode.so` | 仅链接期 `-l:libnode.so`，不打包 |
| NDK | r28c（`28.2.13676358`，与 runtime 24.22.1 同款；矩阵内随 runtime 对齐） | `aarch64-linux-android24-clang++` |
| Android API | 24 | 与 runtime `minSdk` 一致 |
| libc | bionic：**无 libutil**，`openpty`/`forkpty` 在 `libc` | 无需额外 `-lutil` |

### 3.3 构建命令（可复现配方）

```bash
# 工具链
CLANG="$NDK/toolchains/llvm/prebuilt/<host>/bin/aarch64-linux-android24-clang++"

"$CLANG" -std=gnu++17 -fPIC -shared -O2 \
  -I <node-v<ver>-headers>/include/node \
  -I <node-addon-api> \
  -DNAPI_DISABLE_CPP_EXCEPTIONS \
  -DNODE_ADDON_API_DISABLE_DEPRECATED \
  src/unix/pty.cc \
  -Wl,--no-as-needed \
  -L <dir-containing-libnode.so> -Wl,-l:libnode.so \
  -o libpty_node.so
```

随后 `llvm-strip --strip-unneeded`（产物约 90KB 量级）。

### 3.4 已实测的关键踩坑（必须固化进构建脚本，不是"注意事项"而是门禁）

1. **不得定义 `NODE_ADDON_API_ENABLE_MAYBE`**：node-pty 使用 `node_addon_api_except` 变体；加了该宏会把
   `CallbackInfo::operator[]().As<T>()` 等变成 Maybe 型，导致整面编译错误。
2. **必须 `DT_NEEDED libnode.so`**：
   `-Wl,--no-as-needed … -Wl,-l:libnode.so`。宿主以 `RTLD_LOCAL` 加载引擎时，pty 件里数十个
   `napi_*` 未定义引用只有靠"按 soname 复用已加载 `libnode.so`"才能在 `dlopen` 时解析成功。
   产物门禁必须验证 `NEEDED` 中存在 `libnode.so`。
3. **只能从 nativeLibraryDir 加载**：未压缩库（`useLegacyPackaging=false`）时代理路径/数据目录直接
   `dlopen` 受 SELinux 限制；消费侧应以 soname 走应用 linker namespace（`System.loadLibrary("pty_node")`
   或等价路径）。本工程的职责是把 `.so` 以正确名字放进 AAR 的 `jni/arm64-v8a/`。
4. **NODE_MODULE_VERSION 一致性**：头文件版本与运行时不一致会在加载期直接报模块 ABI 不符；
   lock 同时记录 `nodeAbi`（NODE_MODULE_VERSION）与 `node` 版本，门禁/文档双重提示。
5. **bionic 无 libutil**：不要移植 glibc 的 `-lutil`；`forkpty/openpty` 在 bionic libc。

### 3.5 不支持与降级

- 不提供 Windows conpty / macOS / Linux 桌面原生件——本仓库仅 Android arm64。
- 不提供纯 JS 回退：PTY 无纯 JS 实现；原生件缺失时，消费方应**结构化报"不支持"**，而不是静默降级
  （该决策属于消费方，但本工程在 README 明确建议）。
- devpts `ptmxmode=000`、slave 端 `ioctl(unlockpt/grantpt)` 等设备期行为差异由 node-pty 内部处理；
  本工程只保证原生件可加载、可 `forkpty`，不承诺所有 ROM 的终端全功能（边界写入 release notes）。

## 4. 唯一事实源：`pty.lock.json`

镜像 `aosp-node-runtime/runtime.lock.json` 的纪律：**版本 + 大小 + sha256 + 配对 Node + ELF 门禁 +
出处**集中在仓库根一个文件，二进制不入库。

```jsonc
{
  "$comment": "PTY companion single source of truth: version mirrors the paired node-runtime. Binaries are NOT committed; CI builds libpty_node.so and tools/provision.mjs deploys it.",
  "active": { "node": "24.22.1", "abi": "arm64-v8a" },
  "releases": [
    {
      "node": "24.22.1",                 // = 制品版本 = 配对 runtime 版本
      "nodeAbi": 137,                    // NODE_MODULE_VERSION
      "abi": "arm64-v8a",
      "androidApi": 24,
      "name": "libpty_node.so",
      "size": 0,
      "sha256": "<filled by CI>",
      "pairedRuntime": {
        "coordinates": "io.github.fellow99:node-runtime:24.22.1",
        "libnodeSoname": "libnode.so"
      },
      "builtFrom": {
        "nodePty": "node-pty@1.x (npm, source unmodified; unix target src/unix/pty.cc)",
        "nodeHeaders": "node-v24.22.1-headers.tar.gz (nodejs.org dist)",
        "nodeAddonApi": "<resolved version>",
        "ndk": "r28c (28.2.13676358)",
        "flags": "clang++ -std=gnu++17 -fPIC -shared -O2 -DNAPI_DISABLE_CPP_EXCEPTIONS -DNODE_ADDON_API_DISABLE_DEPRECATED -Wl,--no-as-needed -Wl,-l:libnode.so",
        "stripped": "llvm-strip --strip-unneeded"
      },
      "gates": {
        "eTypeEtDyn": true,
        "ptInterp": 0,
        "eMachineAArch64": true,
        "neededLibnode": true,           // DT_NEEDED 含 libnode.so（本工程特有硬门禁）
        "undefinedNapiResolvable": true, // napi_* 仅作未定义引用、交由 libnode.so 解析
        "sha256Match": true,
        "sizeMatch": true,
        "pageAlign16k": true
      },
      "build": 0,                         // 同 Node 版本重发的构建序号（§8.3）
      "release": { "tag": "v24.22.1", "url": "<github release>", "archive": "node-pty-v24.22.1-android-arm64-v8a.tar.gz" },
      "mavenCentral": { "coordinates": "io.github.fellow99:node-pty:24.22.1", "published": false },
      "status": "draft"
    }
  ],
  "matrix": {
    "minSdk": 24,
    "abi": ["arm64-v8a"],
    "note": "Companion to node-runtime; consumers MUST pair node-pty:<node> with node-runtime:<node> (identical NODE_MODULE_VERSION). Loaded from nativeLibraryDir via soname; do not dlopen from writable data dirs."
  }
}
```

门禁取舍：沿用 runtime 的 ELF 检查（ET_DYN / 无 PT_INTERP / aarch64 / soname / 16KB 对齐 / sha / size），
**新增 `neededLibnode`** 为本工程不可妥协项；`undefinedNapiResolvable` 用 `readelf`/ELF 解析核对
`napi_*`、`node_*` 处于未定义符号表（说明设计上由引擎提供，而非静态塞入）。

## 6. 构建、投放与发布流水线

### 6.1 本地可复现构建

```bash
# 1) 取源（node-pty npm 源不改；node headers 与配对 runtime 同版本）
node scripts/fetch-node-pty-source.mjs --node 24.22.1 --node-pty 1.x

# 2) 交叉编译（NDK r28c；链接期需要对应 libnode.so，可从 node-runtime release/本地投放取）
scripts/build-pty-android.sh --node 24.22.1 --api 24 \
  --libnode <path-to>/libnode.so --out build/out/libpty_node.so

# 3) 投放进模块 + 写/校验 lock
node tools/provision.mjs --out node-pty/src/main/jniLibs --from build/out/libpty_node.so
node tools/provision.mjs --check
node tools/provision.mjs --inspect build/out/libpty_node.so
```

`provision.mjs` 退出码纪律与 runtime 一致：`0` 全过 · `2` 门禁不合格 · `1` 用法/IO 错误。

### 6.2 GitHub Actions（`build-pty-android.yml`）

- 触发：`workflow_dispatch`，入参 `node_version`（默认取 lock 的 `active.node`）、`android_api`(24)、
  `node_pty_version`、`prerelease`。
- 关键步骤：
  1. 装 NDK r28c + host 构建工具（`build-essential file`）。
  2. **拉取配对的 `libnode.so`**：优先从 `aosp-node-runtime` 同版本 GitHub Release 资产取（只用于链接），
     并校验其与 runtime lock 的 sha；取不到则失败（绝不允许 against 错误引擎版本编出 pty）。
  3. 下载 node headers（同版本）+ node-pty npm 源 + node-addon-api。
  4. 编译 → strip → ELF/DT_NEEDED 门禁 → 产出 `node-pty-v<node>-android-arm64-v8a.tar.gz`。
  5. 回写/更新 `pty.lock.json` 的 size/sha/gates，发布 GitHub Release 资产。
  6. （`RELEASE=true` 时）发布到 Maven Central，坐标 `io.github.fellow99:node-pty:<node>`。
- 签名/Token 仅从用户级 `~/.gradle/gradle.properties` 读取，默认 `RELEASE=false` 防误发——同 runtime。

### 6.3 版本与重发

- 新增 Node 版本 = 在 lock `releases` 增项 + 以该版本触发 CI；`active.node` 跟随最新受支持版本。
- 同一 Node 版本下仅升级 node-pty 补丁：递增 `build`（构建序号），Maven 坐标 version 保持 Node 版本，
  通过 Classifier 或发布序号区分（默认不重发已发布版本；确需修复走新构建序号并在 release notes 标注）。
- **引擎升版是 pty 的强制重编事件**：runtime 发布新版本后，pty 必须在同版本补出配对件，
  否则消费方升级 runtime 即丢失终端能力。两者发布节奏绑定（见 §9 里程碑）。

## 7. 消费方接入契约（通用，不针对任何特定产品）

### 7.1 依赖

```kotlin
dependencies {
    val nodeVer = "24.22.1"              // runtime 与 pty 必须同版本
    runtimeOnly("io.github.fellow99:node-runtime:$nodeVer")
    runtimeOnly("io.github.fellow99:node-pty:$nodeVer")
}
```

APK 解包后二者同在 `nativeLibraryDir`：`libnode.so` 与 `libpty_node.so`。

### 7.2 版本配对校验（建议在消费方 CI/启动期做）

- 断言两依赖解析到的版本字符串完全相等；
- 运行期可在加载 pty 前核对 `process.versions.modules`（NODE_MODULE_VERSION）与 lock 中 `nodeAbi` 一致。

### 7.3 原生件加载与 node-pty JS 适配

上游 node-pty 的 JS 运行时（`lib/`，随消费方自身的 npm 依赖树提供）默认按
`build/Release/pty.node` 定位原生件；而 AAR 投放到 nativeLibraryDir 的是 `libpty_node.so`。
消费方需在 `require('node-pty')` **之前**安装一个定位适配，使其从引擎 linker namespace 取到本件，例如：

- 首选：以 soname 预加载 `System.loadLibrary("pty_node")`（Kotlin/Java 侧，应用 linker namespace，
  命中合规只读执行位），随后让 node-pty 的原生加载命中已加载库；或
- 在 Node 侧覆盖 node-pty 的原生件解析路径（其 `utils.js` 支持按平台/文件定位），指向
  `<nativeLibraryDir>/libpty_node.so` 的绝对路径；该路径由宿主桥注入（与定位 `libnode.so` 同源信息）。

> 本工程交付到"`.so` 在 AAR 且带正确 `DT_NEEDED`"为止；上述适配属各宿主桥/运行时封装职责。
> README 需给出最小加载示例（伪代码级），但不内置任何产品特定代码。

### 7.4 运行期事实与边界

- 加载成功即可 `forkpty`：`unlockpt/grantpt → setsid → TIOCSCTTY → exec shell`（由 node-pty 完成）。
- 不同 ROM 的 devpts/SELinux 形态可能影响 slave 端可用性；消费方应在其自检里跑一次
  "spawn `/system/bin/sh -c 'echo PTY_ROUNDTRIP_OK'` → 收到回显" 的最小回程探针，作为是否开放终端的判据。
- 原生件缺失/ABI 不符/SELinux 拒绝，均应**结构化上报**，不要静默回退到假终端。

## 8. 质量门禁汇总

| 门禁 | 判据 | 在哪强制 |
|---|---|---|
| ELF 形态 | `ET_DYN`、无 `PT_INTERP`、`e_machine=aarch64`、16KB 对齐 | `tools/provision.mjs` + CI |
| 引擎绑定 | `DT_NEEDED` 含 `libnode.so`；`napi_*` 未定义引用由引擎解析 | provision（本工程特有）+ CI |
| ABI 配对 | node headers 版本 = `active.node` = 配对 runtime；NODE_MODULE_VERSION 记录在 lock | CI 拉取 runtime 资产时校验 |
| 出处完整 | node-pty / node-addon-api / NDK / flags / strip 全记录 | `pty.lock.json` review |
| 不入库 | `jniLibs/**/*.so` 被忽略，二进制只来自 CI 资产 | `.gitignore` + review |
| 可复现 | 干净 runner 上一条 workflow 可重出同 sha 口径产物 | CI |
| 许可 | node-pty MIT、node-addon-api、NAPI 第三方声明齐全 | `THIRD-PARTY-NOTICES.md` |
| 发布卫生 | `RELEASE=false` 默认；Token/GPG 不入库 | gradle.properties / publish |

## 10. 开放问题（立项后需拍板）

1. node-pty 上游版本钉选策略：固定一个经验证版本（如 1.1.0）还是跟最新稳定？建议**固定 + 显式升级**，
   升级即一次带回归的 M 级动作。
2. 是否在本仓同时提供 node-pty 的 **JS 运行时封装**（`lib/`）作为 AAR 资产或独立 npm 包，
   还是完全交由消费方 npm 依赖树。初版建议**只发原生 `.so`**，JS 由消费方按同版本 node-pty 引入，
   避免 JS/原生版本错配；如多个消费方重复踩加载适配，再评估提供统一加载垫片。
3. 多 ABI（x86_64 / armeabi-v7a）与 32 位 API 矩阵的启用时机：跟随 runtime，不超前。
4. 同 Node 版本重发的分发约定（classifier vs build 序号）需在 M2 前与发布流程一并定死。
